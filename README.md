# Deepfake Detection Toolkit

Two lightweight PyTorch pipelines built on the Hugging Face [`saberzl/SID_Set`](https://huggingface.co/datasets/saberzl/SID_Set) dataset:

- **Classification** – predicts `Real`, `Synthetic`, or `Tampered` frames with a compact CNN.
- **Segmentation** – localises tampered regions with a slim U-Net.

Both share a common configuration system, logging utilities, dataset manager, and output conventions.

---

## Repository Layout

- `src/deepfake/` – package containing the task pipelines, data helpers, visualisation utilities, and configuration schema.
- `configs/` – runnable YAML overrides (e.g. `classification.yaml`, `segmentation.yaml`).
- `outputs/` – default destination for logs, checkpoints, and result artefacts (safe to wipe between runs).
- `docs/` – API and configuration documentation.
- `notebooks/` – exploratory Jupyter notebooks.

## 1. Environment Setup
This guide walks you through setting up the environment for using the Deepfake Toolkit, including both CPU and GPU configurations.

### 1. Conda
Create a new Conda environment with Python 3.12:
```bash
conda create -n deepfake-env python=3.12 -y
```

Activate the environment:
```bash
conda activate deepfake-env
```

#### 2. Editable Installation (Development Mode)
If you want to install the package in editable mode for development purposes, use one of the following commands depending on your hardware:

```bash
pip install -e .
```
Or
```bash
conda install pytorch torchvision pytorch-cuda=12.8 -c conda-forge -c nvidia
pip install -e .
```

#### 3. Installing Deepfake CLI and Project Dependencies
Alternatively, if you want to install the released version of the package from PyPI or another package index, follow these instructions for a stable, versioned installation without modifying the source code. This is the recommended approach if you are a user or deploying the tool.

##### 1. CPU Installation

If you are using a CPU-only machine, install the CPU dependencies with:

```bash
pip install deepfake-toolkit
```

#### 2. GPU Installation
If you have a compatible GPU and CUDA installed, install the GPU-enabled dependencies with:
```bash
conda install pytorch torchvision pytorch-cuda=12.8 -c conda-forge -c nvidia
pip install deepfake-toolkit
```

#### 4. Using a Virtual Environment (Optional)

If you prefer using a Python virtual environment instead of Conda:
```bash
python -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e .
```

### 7. Notes

- CUDA support is auto-detected when available; otherwise, the toolkit defaults to CPU.
- Choose the installation method (CPU or GPU) based on your hardware capabilities.
- For Conda users, the recommended Python version is 3.12 to ensure compatibility.

## 2. Configuration (YAML Required)

- Every run must provide `--config <file>`, pointing to a YAML override under `configs/`.
- The packaged defaults live under `src/deepfake/config/default.yaml`; do not edit this file directly.
- Copy any config to create variants, e.g. `cp configs/classification.yaml configs/large-batch.yaml`, then adjust hyperparameters or output paths inside the copy.
- Runs are isolated automatically under a per‑run subfolder (`paths.run_name`). You can still override `paths.model_path`, `paths.results_dir`, and `paths.logging_dir` in YAML to control the base directories (e.g., include a `<task>` segment).
- `data.use_streaming` currently falls back to on-disk datasets (a warning is emitted) to avoid upstream streaming shutdown issues.

See `docs/Configuration.md` for field-by-field details.

## 3. Run Pipelines

Use the installed console script (after `pip install -e .`):

```bash
# classification
deepfake-cli --train --task classification --config configs/classification.yaml
deepfake-cli --eval  --task classification --config configs/classification.yaml

# segmentation
deepfake-cli --train --task segmentation --config configs/segmentation.yaml
deepfake-cli --eval  --task segmentation --config configs/segmentation.yaml
```

Recommended with a fixed run name (ensures eval loads the same checkpoint):

```bash
export RUN_NAME=250104_142355

# classification
deepfake-cli --train --task classification --config configs/classification.yaml
deepfake-cli --eval  --task classification --config configs/classification.yaml

# segmentation
deepfake-cli --train --task segmentation --config configs/segmentation.yaml
deepfake-cli --eval  --task segmentation --config configs/segmentation.yaml
```

Evaluation notes

- The evaluator loads the checkpoint from `cfg.paths.model_path`, which includes the per‑run folder. If the configured model is missing and no run is specified, eval automatically reuses the latest training run for that task—no extra run directory is created. For example, after

```bash
deepfake-cli --train --task classification --config configs/classification.yaml   # run name auto-generates, e.g. 250104_142355
deepfake-cli --eval  --task classification --config configs/classification.yaml   # reuses 250104_142355 automatically
```

the evaluation metrics and plots land in `outputs/results/classification/250104_142355/` alongside the training history, and no extra run folder is created.

To be explicit, set the run name to the training run so eval finds the correct model:

```bash
export RUN_NAME=250104_142355
deepfake-cli --eval --task classification --config configs/classification.yaml
```

- By default, eval writes metrics and plots into the same run’s results folder. To keep eval outputs separate, change only the base dirs in your YAML while keeping the training run name:

```yaml
# example override for classification eval
paths:
  run_name: <training_run_name>
  results_dir: outputs/results/classification/eval
  logging_dir: outputs/logs/classification/eval
```

The effective eval outputs will go under `.../eval/<training_run_name>/`. If no suitable checkpoint is found, evaluation fails fast.

Install the package once (`pip install -e .`) and use `deepfake-cli` for all tasks going forward.

## 4. Outputs and Logging

- Per‑run isolation – every run writes into a subfolder named `cfg.paths.run_name` (auto‑generated if not set). For example:
  - `cfg.paths.results_dir`: `outputs/results/<task>/<run_name>/...`
  - `cfg.paths.logging_dir`: `outputs/logs/<task>/<run_name>/...`
  - `cfg.paths.model_path`: `outputs/models/<task>/<run_name>/best_model.pth`
- Checkpoints – best model saved at `cfg.paths.model_path`. Periodic checkpoints saved every `training.save_interval` epochs under `.../checkpoints/epoch_XXX.pth`.
- Metrics & plots – JSON and images under `cfg.paths.results_dir` (per‑run subfolder). Evaluation metrics are consolidated here.
- Logs – timestamped `.log` files under `cfg.paths.logging_dir`.
- Config capture – a copy of the effective configuration is written to `run_config.yaml` under the results directory of each run.

Control the run name by either setting `paths.run_name` in your YAML, or exporting `RUN_NAME` in the shell. Auto-named runs use a short pattern: `yymmdd_HHMMSS`.

```bash
export RUN_NAME=250104_142355
deepfake-cli --train --task classification --config configs/classification.yaml
```

All destinations are created automatically if they do not exist.

## 5. Troubleshooting & Tips

- Set `training.seed` in your YAML to reproduce runs; the CLI applies it at startup.
- For large streaming jobs, keep `data.use_disk_cache: true` to avoid re-materialising derived splits.
- Authenticate with `huggingface-cli login` if the dataset requires credentials.
- Use `python -m deepfake.utils.config_loader --config <path>` to print the merged configuration for debugging.
